## What changed (per diff map)

Phase-5 introduces a profile-scoped CW typed surface. `ContinueWatchingRecord` (`ContinueWatchingRecord.kt:5-45`) now carries a required `profileId` (rejected in `init` if `<= 0`) plus `parentId` / `contentId` / `provider` / `routingVersion` / `positionMs` / `durationMs` / `episodeContext?` / `clickTimeDisplayMetadata?` / `Source` / `updatedAt`, with `identityKey()` deriving `profile:$profileId:continue-watching:$parentId[:s${season}e${number}]`. `ContinueWatchingSnapshotService.observeContinueWatching(profileId: Int)` (`:358-363`) is the typed-record read API: `require(profileId > 0)`, then `observeSnapshot().map { owned -> if (owned.profileId == profileId) owned.toContinueWatchingRecords() else emptyList() }`. The mapper `ProfileOwnedContinueWatchingSnapshot.toContinueWatchingRecords()` (`:86-138`) stamps every produced record with the snapshot's `profileId` and tags resume rows as `Source.LOCAL` and next-up rows as `Source.SYNTHETIC`. `TrackingProgressService.observeContinueWatchingNextUp()` is now `@Deprecated` (`TrackingProgressService.kt:47-50`) with the message: *"Profile-boundary: use ContinueWatchingSnapshotService.observeContinueWatching(profileId) for profile-scoped CW. This method routes by active tracking provider only and is consumed internally by ContinueWatchingSnapshotService."*. The single in-tree call site is at `ContinueWatchingSnapshotService.kt:256` inside the live-snapshot flow, suppressed via `@Suppress("DEPRECATION")` at `:252`. CW writes emit `continue_watching.snapshot_write` from `emitWrite(profileId, recordCount)` (`:1344-1364`) at three call sites: persisted-load normalization (`:325`), `observeSnapshot` first-emit warm path is *not* a write — writes are at `:325` (normalized re-persist) and `:939` (`persistRawSnapshot`). CW reads emit `continue_watching.snapshot_read` from `emitRead(profileId, recordCount)` (`:1366-1386`) on `observeSnapshot()`'s `onStart` (`:343-355`). Profile switch resubscribes via `profileManager.profileSwitched.collectLatest { profileId -> markProfileAwaitingLiveReset(profileId); persistedSnapshotReady.value = false; loadPersistedSnapshotForActiveProfile(clearWhenMissing = true) }` (`:189-197`); on `clearWhenMissing = true` and no persisted file the `rawSnapshotState` and `snapshotState` are reset to a fresh `ProfileOwnedContinueWatchingSnapshot(profileId)` and `lastRefreshRequestMs = 0L` (`:314-319`). The live-snapshot pipeline is additionally gated by `canPublishLiveSnapshot(profileId)` (`:1085-1099`) so a profile that just switched cannot publish a live emission until it has first observed a remote-snapshot reset (`hasLoadedRemoteSnapshot=false` followed by a successful reload), preventing the previous profile's in-flight remote data from leaking across the switch.

## Findings

### F-G-01 (cross-ref F-RF-03 / F-09-1): Profile-scoped CW read API has zero production callers — Home VM filters manually on a wider flow

- **Severity:** P1
- **Evidence:**
  - `ContinueWatchingSnapshotService.observeContinueWatching(profileId: Int)` is declared at `ContinueWatchingSnapshotService.kt:358-363`. The body is correct: `require(profileId > 0)` and `observeSnapshot().map { owned -> if (owned.profileId == profileId) owned.toContinueWatchingRecords() else emptyList() }`.
  - `grep -rn "observeContinueWatching(" --include="*.kt" app/src/main/` returns exactly two production hits: the declaration at `ContinueWatchingSnapshotService.kt:358` and the deprecation `message` text in `TrackingProgressService.kt:48`. **Zero production callers.**
  - Home VM CW collector (the only first-class CW UI consumer): `HomeViewModelContinueWatching.kt:71-118` (`loadContinueWatchingPipeline()`) calls `continueWatchingSnapshotService.observeSnapshot().collectLatest { ownedSnapshot -> ... if (ownedSnapshot.profileId != activeHomeProfileSession.profileId) return@collectLatest ... }`. The collector receives the `ProfileOwnedContinueWatchingSnapshot` (which carries the snapshot's owning `profileId`) and discards it if the id does not match the captured `activeHomeProfileSession.profileId`.
  - Second production consumer: `AndroidTvFeedCatalogService.kt:150` reads `continueWatchingSnapshotService.observeSnapshot().first().snapshot` for Android TV recommendations *without any profile filter*. The implicit assumption is that the snapshot is always for the active profile — which is true today only because `loadPersistedSnapshotForActiveProfile` and the live-emission pipeline both tag with `activeProfileId()`, but the recommendations service itself does not assert it.
  - The only test that exercises `observeContinueWatching(profileId)` directly is `ContinueWatchingProfileScopedQueryTest.kt:8-76`, which calls the *mapper* (`toContinueWatchingRecords()`) on a hand-built `ProfileOwnedContinueWatchingSnapshot` — it does not exercise the `observeContinueWatching(profileId)` flow path itself or the cross-profile filter.
- **Violated contract:** Lane G Contract 2 (production read API). The typed `ContinueWatchingRecord` surface is unused; the entire UI path consumes the untyped `ContinueWatchingSnapshot` via the parameterless wrapper. This means the only thing standing between a foreign-profile snapshot and the UI is the manual `if (ownedSnapshot.profileId != activeHomeProfileSession.profileId)` guard in `HomeViewModelContinueWatching.kt:75-78`. A future refactor that drops or inverts that guard (e.g., during a viewmodel split) will silently downgrade the boundary check to nothing.
- **User-visible impact:** None today — the snapshot is always tagged with the correct profile id at write time and the manual guard catches the mismatch. The latent risk: any code path that consumes `observeSnapshot()` without the explicit `profileId` check (today: `AndroidTvFeedCatalogService`) will surface the active profile's snapshot regardless of which profile id the caller intended. If `AndroidTvFeedCatalogService` is ever invoked from a background worker started under profile A and the user has since switched to profile B, the recommendations job will publish profile B's CW into the Android TV channels labeled as profile A's recommendations.
- **Required fix:** Route every CW read through `observeContinueWatching(activeProfileId)`. (a) Update `HomeViewModelContinueWatching.kt:73` to call `continueWatchingSnapshotService.observeContinueWatching(activeHomeProfileSession.profileId).collectLatest { records -> ... }`. The pipeline currently consumes `ContinueWatchingSnapshot` (with its `displayMetadataByItemKey`, `traktUpNextItems`, `nextUpItems`) so it would need either (a1) a richer typed surface — extend `observeContinueWatching` to return a typed `ProfileOwnedContinueWatchingView` — or (a2) keep `observeSnapshot()` for the metadata-rich path but introduce a typed `observeProfileScopedSnapshot(profileId)` that filters at the service boundary. (b) Either way `AndroidTvFeedCatalogService.kt:150` must be passed the explicit profile id and call the filtered overload. (c) Delete the bare `observeSnapshot()` overload — or keep it with a `@RestrictTo` / internal visibility to prevent further accidental use.
- **Test or report that should catch it:** Add `ContinueWatchingObserveProfileScopedTest` that subscribes to `observeContinueWatching(profileId = 2)` while the active snapshot is owned by `profileId = 1`, asserts an `emptyList()` emission, then `setActiveProfile(2)`, asserts the `profileId = 2` records flow. Also add a `Lint` rule (or boundary-audit golden test) banning `observeSnapshot().collect(...)` outside `ContinueWatchingSnapshotService` itself.

### F-G-02: `continue_watching.snapshot_read` has no test coverage

- **Severity:** P2
- **Evidence:**
  - Production emission at `ContinueWatchingSnapshotService.kt:343-355` (`onStart { emitRead(...) ... }`) and emitter at `:1366-1386` is correctly wired through `traceSink` after `installTraceSink(...)`.
  - `grep -rn "snapshot_read" --include="*.kt" app/src/test/` returns **zero hits**. Compare to `snapshot_write`, which has both a runtime ordering test (`ContinueWatchingSnapshotServiceProfileBoundaryTest.kt:227,264`) and validator-rule coverage (`TraceValidationRulesTest.kt:198-205`).
  - The `payload` keys are not asserted anywhere: no test confirms that `profileHash`, `profileId`, `recordCount`, `source = "OBSERVE_SUBSCRIBE"` all appear in the envelope. A typo in the key name or a payload-shape change (e.g., dropping `profileHash` for a privacy refactor) would not fail any test.
  - Subtle correctness concern in the production code: `recordCount` is read from `snapshotState.value` at *subscription* time, but the actual emission is gated by `combine(snapshotState, persistedSnapshotReady) { ... takeIf { ready } }.filterNotNull()`. If `persistedSnapshotReady = false` at subscribe time (e.g., during a profile switch), the `snapshot_read` event is emitted with the *pre-switch* `recordCount`, and the subscriber will only receive the post-switch snapshot later. This drift between the trace event and the actual delivered data is not asserted or documented.
- **Violated contract:** Lane G Contract 5 — the production guard exists but no automated guard prevents regression. Cross-references the Lane I trace-mode contract that every CW read should be observable.
- **User-visible impact:** None today (the trace bundle behavior is opaque to end users). Operator impact: a drift between `snapshot_read.recordCount` and what the UI actually rendered would mislead trace-bundle analysis ("the user observed 5 CW records but the UI only shows 2 — what filtered them?") when in fact the trace event was emitted before the data was even delivered to the subscriber.
- **Required fix:** Add `ContinueWatchingSnapshotReadTraceTest` that installs a capturing `RuntimeTraceSink`, subscribes to `observeSnapshot()`, asserts a single envelope with `eventType = "continue_watching.snapshot_read"`, `payload.source = "OBSERVE_SUBSCRIBE"`, `payload.profileId = activeProfileId`, non-blank `payload.profileHash`, and `payload.recordCount` matching the snapshot the subscriber actually received (which means the test must wait until `persistedSnapshotReady = true` before asserting). Either (a) move the `emitRead(...)` call inside the `combine { ... takeIf { ready } }.filterNotNull()` so the recorded `recordCount` matches the delivered snapshot, or (b) document the drift explicitly in the emitter doc-comment.
- **Test or report that should catch it:** New test as above; also add a validator rule "every `continue_watching.snapshot_read` payload must include `{profileHash, profileId, recordCount, source}`" alongside the existing write-side rule.

### F-G-03: `snapshot_write.recordCount` excludes `traktUpNextItems` — undercount on Trakt-driven rails

- **Severity:** P3
- **Evidence:**
  - Two write-side `emitWrite(...)` call sites: `ContinueWatchingSnapshotService.kt:325-328` (post-load normalize) and `:939-942` (`persistRawSnapshot`). Both compute `recordCount = hydrated.resumeItems.size + hydrated.nextUpItems.size`.
  - `ContinueWatchingSnapshot` has three rails: `resumeItems`, `nextUpItems`, and `traktUpNextItems` (`:67-75`). The third (synthetic Trakt up-next rail, populated from `trackingProgressService.observeSyntheticContinueWatchingNextUp()` at `:257`) is not counted in the trace event.
  - `read`-side `emitRead` at `:347` makes the same omission: `recordCount = current.snapshot.resumeItems.size + current.snapshot.nextUpItems.size`.
  - The `toContinueWatchingRecords()` mapper itself (`:86-138`) only iterates `resumeItems + nextUpItems` — `traktUpNextItems` are *not* lifted into typed records either, despite being a real on-screen rail (consumed via `state.traktUpNextItems` in `HomeViewModelContinueWatching.kt:95-97, 107`).
- **Violated contract:** Lane G Contract 4 (loose: the event emits, but the count under-reports the rendered surface). More importantly, this is a typed-surface coverage gap: the synthetic Trakt up-next rail is invisible to the typed `ContinueWatchingRecord` API and to trace bundles. An operator analyzing why a user sees 8 CW tiles but the trace shows `recordCount=5` will conclude data loss when the truth is `5 resume + nextUp + 3 traktUpNext` — a documentation/observability bug, not a data bug.
- **User-visible impact:** None directly. Operator impact: trace-bundle CW counts are not the rendered count, with a silent deficit equal to `traktUpNextItems.size`.
- **Required fix:** Either (a) include `traktUpNextItems.size` in `recordCount` (and add a `recordCount` payload key per rail: `resumeCount`, `nextUpCount`, `traktUpNextCount`); or (b) extend `toContinueWatchingRecords()` to lift `traktUpNextItems` into records (with a new `Source.SYNTHETIC_TRAKT_UP_NEXT` or similar) so the typed surface matches the rendered surface. Option (b) also addresses a latent gap in F-G-01 — the typed read API would then represent everything the UI actually shows.
- **Test or report that should catch it:** Add to `ContinueWatchingProfileScopedQueryTest` a case with non-empty `traktUpNextItems` asserting either the expected count in records or the documented exclusion. Add a trace-validator rule that `snapshot_write.recordCount` equals the sum of the three rail sizes (or all three keys are present).
