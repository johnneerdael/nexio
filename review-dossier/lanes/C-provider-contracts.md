## What changed (per diff map)

`data/integration/**` is the phase-A consolidation: every provider now constructs an `IntegrationSpec` (cached) or `IntegrationCallSpec` (call-only) and routes through `IntegrationRuntime.get(...)` / `runtime.call(...)`. `TmdbIntegrationProvider` and `TvdbIntegrationProvider` carry localization-policy versioning into operation/cache keys; Kitsu adds an episode-pagination loop; the metadata adapters (`TmdbMetadataProviderAdapter`, `TvdbMetadataProviderAdapter`, `KitsuMetadataProviderAdapter`) wrap the integration providers and parse `tmdb:`/`tvdb:`/`kitsu:` prefixes via `MetadataProviderTargetIds`. Trakt and Simkl scope authenticated calls with `IntegrationScope.Account(profileId, provider, credentialHash)` and `accountCacheKey()` / `accountOperationKey()` helpers; device-auth flows on Trakt downgrade to `IntegrationScope.Profile(...)`. The two premium poster providers (`Rpdb`, `TopPosters`) share a single `PosterTransport` (OkHttp) confined to the `data/integration/posters/transport` subpackage.

## Findings

### F-C-01: TMDB person/company helpers bypass `IntegrationRuntime`

- **Severity:** P1
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/tmdb/TmdbIntegrationProvider.kt:740-788` — four functions call `tmdbApi.*` via the local `loadResponse(...)` helper (`:1385-1403`) without ever wrapping the call in `runtime.get(spec)` or `runtime.call(spec)`:
  - `loadPersonDetails(personId)` → `tmdbApi.getPersonDetails(...)` (`:740-749`)
  - `loadPersonCombinedCredits(personId)` → `tmdbApi.getPersonCombinedCredits(...)` (`:751-760`)
  - `searchPeople(query)` → `tmdbApi.searchPeople(...)` (`:762-777`)
  - `searchCompanies(query)` → `tmdbApi.searchCompanies(...)` (`:779-788`)
  
  Every other public function on this class wraps the API call in an `IntegrationSpec` (cached) or `IntegrationCallSpec` (call-only); these four are the outliers.
- **Violated contract:** Contract 1 — "All provider calls go through `IntegrationRuntime`." Without the runtime wrapper, the call (a) does not emit `runtime.operation_start` / `runtime.cache_decision`, (b) does not pass through `ProfileBoundaryEnforcer`, (c) is not subject to the global circuit breaker / rate-limiter (Lane A), (d) cannot be observed by `RuntimeTraceValidator`.
- **User-visible impact:** Person browse and company browse flows (DETAIL secondary screens; search results) hit the TMDB API without observability. A circuit-broken TMDB account or a rate-limit storm during search will not be reflected in trace mode and will not respect runtime-level retry/backoff. The trace-validator rule `RuntimeCallHasApiShapeId` cannot fire for these requests, masking the gap from CI.
- **Required fix:** Wrap each of the four functions in `runtime.call(IntegrationCallSpec(provider = TMDB, apiShapeId = TmdbApiShapes.PERSON_DETAIL | PERSON_COMBINED_CREDITS | …, operationKey = "tmdb.person.detail" | …, workClass = USER_VISIBLE, call = { … }))`. The constants `TmdbApiShapes.PERSON_DETAIL`, `PERSON_COMBINED_CREDITS` already exist (`IntegrationApiShapes.kt:111-112`) — they are simply unused. Add `TmdbApiShapes.SEARCH_PEOPLE` and `SEARCH_COMPANIES` (currently missing from the registry — F-C-02 covers this) for the search variants.
- **Test or report that should catch it:** Add a Detekt rule banning `tmdbApi.*` calls outside an enclosing `runtime.call` / `runtime.get` lambda; static-grep CI step asserting `runtime.(get|call)\(` precedes every `tmdbApi.` call site. Plus a `TmdbIntegrationProviderRuntimeContractTest` that records all `runtime.operation_start` events emitted by exercising every public method with a fake `IntegrationRuntime` and asserts the call list is non-empty.

### F-C-02: `apiShapeId` literals bypass the `*ApiShapes` policy registry

- **Severity:** P2
- **Evidence:**
  - `TvdbIntegrationProvider.kt:677,686,695,698,701` — five reference-records branches use string literals (`"tvdb.reference.artwork_statuses"`, `"tvdb.reference.series_statuses"`, `"tvdb.reference.source_types"`, `"tvdb.reference.entity_types"`, `"tvdb.reference.company_types"`) instead of registry constants. `TvdbApiShapes` (`IntegrationApiShapes.kt:136-153`) declares `REFERENCE_ARTWORK_TYPES`, `REFERENCE_GENRES`, `REFERENCE_LANGUAGES`, `REFERENCE_CONTENT_RATINGS`, `REFERENCE_SEASON_TYPES` but is missing the five above.
  - `TraktIntegrationProvider.kt:89,102,116,138,153,162,170,181,196,215,242,262,281,298,323,358,376,393,407,420,434,447,460,473,486,498,511,522,535,548,562,575,588,605,620,633,644,656,668,681,694,708,959,997,1036,1089,1141` — most operation/shape strings are literal. `TraktApiShapes` only contains 13 constants (mostly comments / discovery shapes). Cross-checked: only `WATCHLIST_MOVIES`, `WATCHLIST_SHOWS`, `MOVIE_COMMENTS`, `SHOW_COMMENTS`, `CALENDAR_SHOWS`, `TRENDING_*`, `POPULAR_*`, `RECOMMENDED_*` are in the registry; `device_code`, `device_token`, `token_refresh`, `token_revoke`, `user.settings`, `last_activities`, `watched`, `hidden_items`, `episode.history`, `playback`, `user.lists`, `user.list_create`, `history.add`, `scrobble`, `checkin`, `popular.lists` etc. are not.
  - `SimklIntegrationProvider.kt:128,189,202,215,228` — `"simkl.playback"`, `"simkl.scrobble"` literals; `SimklApiShapes` only declares `LAST_ACTIVITIES`, `DISCOVERY`, `LIBRARY_READ`, `LIBRARY_WRITE`.
- **Violated contract:** Contract 2 — "`apiShapeId` and `operationKey` for each call match the policy registry." With literals, the registry no longer enumerates the surface area: a typo in an apiShapeId silently creates a new shape. Lane A's policy-registry verifier cannot enforce coverage; Lane I's trace validator cannot pre-filter unknown shapes; static analyzers cannot list the API surface from the Kotlin objects.
- **User-visible impact:** Indirect. The IntegrationRuntime accepts any apiShapeId string, so calls succeed; but a mistyped `"trakt.scrobble.start "` (trailing space) would be a different shape than `"trakt.scrobble.start"` and would bypass per-shape rate limits / circuit breakers. Audit/coverage reports under-report Trakt and Simkl footprint by ~70%.
- **Required fix:** Move every literal apiShapeId/operationKey in the integration providers into the corresponding `*ApiShapes` object and reference the constant. For `TvdbApiShapes`, add the five missing reference-record constants. For `TraktApiShapes`, add ~20 missing constants. For `SimklApiShapes`, add `PLAYBACK`, `SCROBBLE`. Add a Detekt rule (or Kotlin compiler plugin) asserting that the `apiShapeId = …` argument to `IntegrationSpec`/`IntegrationCallSpec` constructors must be a property reference, not a string literal.
- **Test or report that should catch it:** `IntegrationApiShapeRegistryCoverageTest` that scans the bytecode for all `IntegrationSpec` constructions and asserts every `apiShapeId` argument resolves to a constant in one of the `*ApiShapes` objects. Plus extend Lane A's runtime-audit harness to error (rather than warn) on unknown shapes.

### F-C-03: ID prefix parser is missing `mal:`, `anilist:`, `anidb:` (and `imdb`/`tt` not validated for metadata adapters)

- **Severity:** P2
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/metadata/MetadataProviderTargetIds.kt:3-23` declares only `tmdbInt`, `tvdbInt`, `kitsu` with `expectedPrefix in {"tmdb", "tvdb", "kitsu"}`. The Lane C contract enumerates `tt`, `tmdb:`, `tvdb:`, `kitsu:`, `mal:`, `anilist:`, `anidb:`. Anime cross-references (e.g., MAL ID 31964 for *Boku no Hero Academia*) cannot be parsed by the metadata adapters; they have to be pre-converted to a `kitsu:` ID by `AnimeIdentityIndex` upstream.
- **Violated contract:** Contract 3 — "ID prefix parsing is correct for `tt`, `tmdb:`, `tvdb:`, `kitsu:`, `mal:`, `anilist:`, `anidb:`." The `tt`-prefixed IMDb path is parsed by `MDBListIntegrationProvider.kt:248-250` only (RF#3 ✅) — there is no central helper. `mal:`/`anilist:`/`anidb:` have no parser at all. Provider adapters silently return `emptyCandidate(this.provider)` for any unknown prefix (`TmdbMetadataProviderAdapter.kt:28`, `TvdbMetadataProviderAdapter.kt:24`, `KitsuMetadataProviderAdapter.kt:28`) — the failure mode is a silent-empty rather than an explicit `unknown_id_format` error.
- **User-visible impact:** If a downstream system (e.g., a Stremio addon) supplies a `mal:31964` ID directly without going through `AnimeIdentityIndex` resolution, the metadata router silently returns an empty candidate and the detail page shows no metadata. No error, no trace event explaining why. Trace mode shows a normal `metadata.route_decision` followed by an empty `metadata.field_selected` — auditors cannot diagnose.
- **Required fix:** Either (a) extend `MetadataProviderTargetIds` with `mal(raw: String?): String?`, `anilist(raw: String?): String?`, `anidb(raw: String?): String?` and `imdb(raw: String?): String?` — and have the provider adapters / `AnimeIdentityIndex` go through the helper — or (b) add an explicit upstream validator that emits `metadata.identity_resolution { success = false, reason = "unsupported_id_prefix" }` when an unknown prefix slips through. Option (a) is cheaper and matches existing pattern.
- **Test or report that should catch it:** `MetadataProviderTargetIdsAnimePrefixTest` covering each anime prefix (success + mismatched-prefix returns null). `MetadataAdapterUnknownPrefixTraceTest` asserting an unsupported `mal:` ID through `MetadataRouterFacade` emits a non-success `metadata.identity_resolution` (option b) or returns the parsed ID via the helper (option a).

### F-C-04: Premium poster providers are not registered as metadata adapters (cross-ref F-50)

- **Severity:** P2 (Lane C visibility; Lane B / Lane I own the merge-side fix)
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/posters/RpdbIntegrationProvider.kt:22-57` and `TopPostersIntegrationProvider.kt:24-60` are `@Singleton` providers wrapped in `IntegrationRuntime` (Contracts 1 & 2 ✅), but they have no corresponding `MetadataProviderAdapter` registration (no `RpdbMetadataProviderAdapter.kt` exists) and `MetadataPrimaryProvider` enum (`MetadataModels.kt:6`) lists only `TMDB`, `TVDB`, `KITSU`. As a result `PosterRatingsUrlResolver.apply(meta, …)` rewrites the `poster` URL directly on the `Meta` model — outside `FieldResolver.resolve(...)`. No `metadata.field_selected { selectedProvider = TOP_POSTERS | RPDB }` event is ever emitted (Path 13 / `13-premium-poster-switch.md:30-33,47,51`).
- **Violated contract:** No Lane C contract directly (Contracts 1, 2, 6, 7 are all ✅ for the providers themselves). Listed here for cross-lane visibility because the metadata-adapter registration gap originates in `data/integration/posters/`. The functional behaviour is correct (the right poster URL renders), but the trace contract `SecondaryDoesNotOverwritePrimary` (`TraceValidationRules.kt:171-185`) cannot validate POSTER overrides because no candidate event is ever emitted.
- **User-visible impact:** Trace mode and audit reports cannot show "TMDB poster was overridden by RPDB" — that audit trail is absent. Validators that rely on `metadata.field_selected` events to assert ownership of POSTER will pass-by-default for premium switches.
- **Required fix:** Register `RpdbMetadataProviderAdapter` and `TopPostersMetadataProviderAdapter` under a new `MetadataPrimaryProvider.RPDB` / `MetadataPrimaryProvider.TOP_POSTERS` (or a separate `MetadataArtworkProvider` axis to avoid widening the enum), and have `PosterRatingsUrlResolver` produce a `MetadataCandidate(provider = …, fields = mapOf(POSTER → FieldValue(url, owner = ARTWORK)))` that the FieldResolver merges. Allow ARTWORK owner to override PRIMARY for POSTER only (the existing `OverridePolicy.protectedFields = {TITLE, OVERVIEW, EPISODE_LIST}` ensures the rest is safe).
- **Test or report that should catch it:** Path 13 contract test asserting `metadata.field_selected { field = POSTER, selectedProvider in {TOP_POSTERS, RPDB} }` is emitted whenever a premium provider is active; trace-validator rule `PremiumArtworkOverrideEmitsFieldSelected`.

### F-C-05: Premium poster cache keys use `apiKey.hashCode()` (cross-ref F-53)

- **Severity:** Nit (Lane C visibility; Lane D co-owns)
- **Evidence:** `PosterRatingsUrlResolver.kt:127,151` (per Path 13) builds `cacheKey` containing `apiKey.hashCode()`. `kotlin.String.hashCode()` is 32-bit and not collision-resistant. The `IntegrationRuntime`-side cache keys for the same providers (`RpdbIntegrationProvider.kt:63`, `TopPostersIntegrationProvider.kt:66`) use `credentialHash(IntegrationProvider, apiKey)` which is a SHA-256-based helper — so the same credential is referenced by two different cache key formats.
- **Violated contract:** None directly in Lane C's seven; reflects an inconsistency in cache-key derivation that touches Contract 7 (artwork keys hardcode `imageLang:en` ✅) by analogy.
- **User-visible impact:** Two RPDB credentials with hash-collisions on `String.hashCode()` (cheap to engineer) would share a cache slot — the second user would see the first user's poster bytes. Practically rare, but consequential when it happens.
- **Required fix:** Replace `apiKey.hashCode()` in `PosterRatingsUrlResolver.buildRpdbPosterUrl` and `buildTopPostersUrl` with `credentialHash(IntegrationProvider.RPDB, apiKey)` / `credentialHash(IntegrationProvider.TOP_POSTERS, apiKey)`.
- **Test or report that should catch it:** `PosterRatingsUrlResolverCacheKeyHashTest` asserting two keys with `apiKey.hashCode()` collisions produce distinct cache slots after the fix.

### F-C-06: Trakt account-scoped cache keys for *global content* duplicate per profile

- **Severity:** Nit
- **Evidence:** `TraktIntegrationProvider.fetchTrendingMovies/Shows`, `fetchPopularMovies/Shows`, `fetchRecommendations`, `fetchPopularLists`, `fetchCalendarShows` (`:758-989`) all use `accountCacheKey(session, "trakt:trending:movies:limit:$limit")` (`:1275-1276`) which prefixes `profile:${session.profileId}:provider:TRAKT:credential:${credentialHash(session)}:`. For *global* trending/popular content the response body is identical across profiles, so cache slots are duplicated per (profile, credential) pair — wasted storage, repeated network on first-load per profile.
- **Violated contract:** None of the seven directly (Contract 6 covers metadata-provider keys, not Trakt). Reflects the broader profile-boundary policy: only *user-specific* Trakt endpoints (`getWatched`, `getWatchlist`, `getUserLists`, `getEpisodeHistory`, `getPlayback`, `getShowProgressWatched`, `addHistory`, …) need account-scoped keys; trending/popular/recommendations vary by `limit` only (recommendations is per-account but trending/popular are global).
- **User-visible impact:** First load of home rows after profile switch incurs ~5 extra Trakt API calls (one per global-content row) even when the cached body is identical to the previous profile's. Scales linearly with profile count.
- **Required fix:** Split the cache-key helper into `accountCacheKey(session, key)` (for user-data endpoints) and `globalContentCacheKey(key)` (for trending/popular/recommendations/calendar). Audit each caller against the [Trakt API "OAuth" column](https://trakt.docs.apiary.io/) — endpoints that return identical bodies regardless of credential go to the global helper. The operationKey can stay account-scoped (for per-account rate-limit / circuit-breaker accounting) while the cache key is global.
- **Test or report that should catch it:** `TraktGlobalContentCacheKeyTest` asserting trending/popular cache keys do not contain `profile:` (mirror of Contract 6 for Trakt-content).
