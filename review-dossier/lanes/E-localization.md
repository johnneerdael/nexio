## What changed (per diff map)

Phase-5 introduces a typed localization layer split across three seams: (1) `LocalizationPolicy` is a per-provider value object (`tvdb()`, `tmdb()`, `kitsu()` factories) carrying `requestedLanguage`, `fallbackLanguage` (always English in some normalized form), `policyVersion = 2`, `allowProviderFallbackForMissingLocalizedFields = false` for *all three* providers, and a per-request cap `maxPerEpisodeTranslationFallbacksPerRequest` (TVDB only, default 8; TMDB/Kitsu hard-coded to 0). (2) `LocalizationResolver.selectField` ranks `LocalizedFieldCandidate`s by `priority(policy)` — `LOCALIZED@requested → LANGUAGE_FALLBACK@en → CANONICAL → ADDON_FALLBACK`, with cross-provider candidates pinned to priority 100 and rejected with reason `cross_provider_fallback_not_allowed_for_missing_localized_field`. (3) Each provider adapter (`TvdbMetadataProviderAdapter`, `TmdbMetadataProviderAdapter`, `KitsuMetadataProviderAdapter`) constructs its own `LocalizationPolicy`, fans out same-provider requested+English fetches through `runtime.get(spec)` (CacheFirst, ttlMs 24h, staleAfterExpiryMs 7d for TVDB translations), feeds candidates to `LocalizationResolver`, and emits `MetadataLocalizationPayloadTrace` records on `ProviderStepResult`. The `metadata.localization_plan` trace helper that previously stitched these together at the orchestrator boundary was deleted in commit `e3a3ab8d7` ("a dead helper was worse than nothing because it implied a validator existed when it could not observe anything").

## Findings

### F-E-01: `LocalizedEpisodeBundle` per-episode fallback counter is computed but not surfaced to trace

- **Severity:** P1
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/metadata/LocalizationModels.kt:42-49` — `LocalizedEpisodeBundle` carries `perEpisodeTranslationFallbacksAttempted: Int` and `maxPerEpisodeTranslationFallbacksAllowed: Int`. `app/src/main/java/com/nexio/tv/data/integration/metadata/TvdbEpisodeLocalization.kt:75-80` populates these from `idsMissingLocalizedFields(...).size` (which itself applies `.take(policy.maxPerEpisodeTranslationFallbacksPerRequest)` at `:107`). `app/src/main/java/com/nexio/tv/data/integration/tvdb/TvdbIntegrationProvider.kt:530-543` orchestrates the bounded `fetchEpisodeTranslationWithTrace` calls. But `app/src/main/java/com/nexio/tv/data/integration/metadata/TvdbMetadataProviderAdapter.kt:62-89` consumes only `bundle.episodes` and `bundle.localizationPayloads`; the two counter fields are dropped on the floor. No trace event carries them. Re-states F-06-01 partial gap and F-TM-06 (test matrix).
- **Violated contract:** Per-episode translation fallbacks bounded — counter visible in trace event when wired (Lane E Contract 4).
- **User-visible impact:** When a TVDB series has many missing localized titles/overviews (e.g., a brand-new season just added in Dutch with most episodes still untranslated), the runtime bounds the per-request burst at 8 (default cap) — but operators reading the trace cannot see *whether the cap was hit* or *how many translations were attempted*. A regression where the cap silently grows (e.g., a future PR raises the default to 32 or removes the `.take(...)`) cannot be caught by trace validation. Conversely, a user complaint "season X never gets translated past episode 8" cannot be diagnosed against trace evidence alone — the operator must reproduce locally and read DEBUG logs.
- **Required fix:** Either (a) extend `MetadataLocalizationPayloadTrace` (`MetadataModels.kt:97`) with optional `perEpisodeFallbacksAttempted`/`perEpisodeFallbacksAllowed` fields and have `TvdbMetadataProviderAdapter` emit a synthesized payload trace per bundle carrying them; or (b) introduce the deferred `metadata.localization_plan` event (see F-E-02) and include the counters in its payload — preferred because the bundle counter and the policy plan are conceptually one event. Test: `TvdbMetadataProviderAdapterTest` asserting that with `policy.maxPerEpisodeTranslationFallbacksPerRequest = 2` and 5 missing-localized episodes, the resulting trace carries `perEpisodeFallbacksAttempted = 2, perEpisodeFallbacksAllowed = 2`.
- **Test or report that should catch it:** New `TvdbLocalizationBundleCounterTraceTest` and an audit assertion in `RuntimeTraceValidator` that the localization plan/payload event for any TVDB SERIES_EPISODES_LANGUAGE step includes the counter fields when the bundle path runs.

### F-E-02: `metadata.localization_plan` event has no production emission site (re-states F-06-01)

- **Severity:** P1
- **Evidence:** `grep -rn "emitLocalizationPlan\|metadata.localization_plan" app/src/main/java` returns zero results. `TraceMetadataEvents.kt:1-209` exposes no localization-plan helper. Commit `e3a3ab8d7` ("feat(trace): wire emitFirstPaint at MetaPreview boundary, remove unwired emitLocalizationPlan") removed the previous helper plus its test (`TraceMetadataEventsLocalizationPlanTest`), explicitly stating "localization-policy tracing is deferred to a separate change that owns the TVDB/Kitsu provider-adapter orchestration site". Boundary map `02-architecture-boundary-map.md:113,139-143` documents "no canonical orchestration site emits `metadata.localization_plan`" — the policy is constructed independently in `TvdbMetadataProviderAdapter.kt:26`, `TmdbMetadataProviderAdapter.kt:30`, `KitsuMetadataProviderAdapter.kt:30` with no shared seam. Per-fetch `MetadataLocalizationPayloadTrace` entries land in `ProviderStepResult.localizationPayloads` (`MetadataExecutionModels.kt:11`) but they describe individual cache decisions, not the *plan* (which language was requested, which fallback was chosen, which policy version, which provider, what the per-episode cap was, whether requested == fallback).
- **Violated contract:** `metadata.localization_plan` event is emitted (Lane E Contract 5).
- **User-visible impact:** Trace bundles uploaded from user devices cannot answer "what localization policy did NEXIO actually apply for this content fetch?". A user complaint "the title is in English even though my profile is set to Dutch" cannot be triaged from trace evidence — the operator can see the per-fetch payloads (English HIT, Dutch MISS_NETWORK_SUPPRESSED) but cannot see the high-level policy state that was applied (was the policy version 2? was `allowProviderFallbackForMissingLocalizedFields = false`? was `requestedIsFallback` true because the profile language fell back to English?). The `PreviewMustNotRouteOrNetwork` validator pattern that worked for `metadata.first_paint` cannot work for localization until this event exists.
- **Required fix:** Two-step. (1) Introduce a `LocalizationOrchestrator` (or extend the `MetadataProviderAdapter` SPI with a `policyForRoute(route): LocalizationPolicy` method invoked from a single seam — `MetadataPlanExecutor` or `ResolverOrchestrator`) so there is *one* canonical site that resolves the policy per route. (2) Add `TraceMetadataEvents.emitLocalizationPlan(route, policy, perEpisodeFallbacksAttempted, perEpisodeFallbacksAllowed, providerFallbackUsed)` and wire it from that seam after policy resolution and after the bundle-level fetch completes (so counters from F-E-01 can ride along). Validator rule: every metadata-route trace span that targets TVDB/TMDB/Kitsu must contain at least one `metadata.localization_plan` event before its first `provider_step` event.
- **Test or report that should catch it:** New `MetadataRouterLocalizationPlanTraceTest` asserting that for a Dutch profile → TVDB SERIES route, the trace contains exactly one `metadata.localization_plan` with `requestedLanguage = "nld"`, `fallbackLanguage = "eng"`, `policyVersion = 2`, and `perEpisodeFallbacksAllowed = 8`.

### F-E-03: `metadata.field_selected` is emitted only by `FieldResolver`, never for per-episode title/overview decisions (re-states F-06-02)

- **Severity:** P1
- **Evidence:** `app/src/main/java/com/nexio/tv/core/metadata/router/FieldResolver.kt:74` — `traceEvents.emitFieldSelected(...)` fires only inside `FieldResolver.resolve(primary, secondary)`, which is called from `MetadataRouterFacade.resolveRequest` (per `04-metadata-execution-audit` and Lane B notes). Per-episode field winners are computed in `LocalizationResolver.selectField` (`LocalizationResolver.kt:6-54`) and stored in `LocalizedEpisodeMetadata.fieldSources` (`LocalizationModels.kt:51-61`) — but `TvdbMetadataProviderAdapter.kt:71-81` only converts these to `MetadataLocalizationFieldTrace` records hung off `episodeLocalization`, which never reach `TraceMetadataEvents.emitFieldSelected`. `TmdbMetadataProviderAdapter.kt:153-172` is structurally identical: builds `MetadataLocalizationFieldTrace` per episode, returns via `episodeLocalization`, no trace emission. `KitsuMetadataProviderAdapter.kt:97-107` likewise builds the trace via `withLocalizationTrace` for series-level title/synopsis but never emits a per-field event. The validator rule at `TraceValidationRules.kt:166-175` ("field_selected lacks ownershipRule") therefore never sees per-episode entries to validate.
- **Violated contract:** Cross-references Lane E Contract 5 (the trace gap is conceptually paired with `metadata.localization_plan`). Direct cross-ref to F-06-02.
- **User-visible impact:** The most operationally important localization decision — *which language won for episode 4 of season 2's title* — is invisible to traces. When an addon-shipped episode title is in the wrong language, support cannot determine from the bundle whether the issue was (a) `LOCALIZED@nl` was missing → fell back to `LANGUAGE_FALLBACK@en` correctly, (b) `LOCALIZED@nl` was a placeholder ("N/A") and the cleaner correctly stripped it, or (c) a bug routed cross-provider candidates that should have been pinned to priority 100.
- **Required fix:** Either (a) emit `metadata.field_selected` inside each provider adapter's per-episode loop after `LocalizationResolver.selectField` returns, with `contentId = "tvdb:$tvdbId:s${season}e${number}"` and the existing `valuePreview` (truncated to 80 chars), `ownershipRule = "localization-resolver: ${selected.fallbackRole.name}"`, and the rejected candidates list; or (b) introduce a sibling `metadata.episode_field_selected` event with the same shape but a structured `(season, episode, field)` tuple. Option (a) keeps the validator rule unchanged.
- **Test or report that should catch it:** New `TvdbMetadataProviderAdapterEpisodeFieldSelectedTraceTest` and a validator rule "every per-episode resolved field must have a matching `metadata.field_selected` event whose `contentId` includes the episode coordinate".

### F-E-04: `Kitsu` localized fetch is single-language; English fallback contract is not enforceable

- **Severity:** P2
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/metadata/KitsuMetadataProviderAdapter.kt:33-65` — Kitsu fetches `fetchEnrichment(...)` once and inside the lambda extracts titles from `attributes.titles` (a map keyed by language code) plus `attributes.canonicalTitle` and `attributes.synopsis`. The language-fallback choice is *delegated to the Kitsu API response shape* (the map already contains all language variants the API returned). `LocalizationPolicy.kitsu(...)` (`LocalizationPolicy.kt:59-74`) sets `fallbackLanguage = NormalizedLanguage("en", "en")`, but there is no second network fetch for English — `selectKitsuTitleField`/`selectKitsuSynopsisField` (in `MetadataAdapterCandidates.kt:271,331`) build candidates entirely from the single response's map. Functionally this is correct *iff* the Kitsu response always contains both requested and English entries; if Kitsu ever returns only the requested language (e.g., a regional anime with no English title yet), there is no English fallback to consume. Contract 3 ("English fallback HITs the cache") is structurally inapplicable here — there is no separate English request to cache-hit.
- **Violated contract:** None hard-violated; latent fragility for Kitsu Contract 1 (English fallback may not exist) and Contract 3 (no separate cache to hit).
- **User-visible impact:** For the vast majority of Kitsu titles this is fine because the API ships titles in `en`, `en_jp`, `ja_jp`, and the requested locale together. For obscure regional content where Kitsu only returns one locale, the user will see the canonical title (often Japanese romaji) with no English fallback even though the policy says English fallback should apply.
- **Required fix:** Either (a) document the Kitsu single-fetch design as intentional and add a `LocalizationPolicy.kitsu(...)` field `fallbackLanguageEmbeddedInResponse: Boolean = true` to make the divergence explicit, or (b) issue a second Kitsu fetch in the requested locale when the response lacks the requested key (rare but correct). Option (a) is cheaper; the policy must then carry a marker so trace consumers can distinguish "no English fetch was needed" from "English fetch was skipped due to bug".
- **Test or report that should catch it:** New `KitsuMetadataProviderAdapterMissingLocaleTest`: synthesize a Kitsu response with only `attributes.titles["ja_jp"]` populated, assert the adapter returns a candidate with the romanized fallback role and a trace marker.

### F-E-05: `TvdbEpisodeLocalization.idsMissingLocalizedFields` truncates *before* sorting — non-determinism risk

- **Severity:** Nit
- **Evidence:** `app/src/main/java/com/nexio/tv/data/integration/metadata/TvdbEpisodeLocalization.kt:100-108` — iteration order is `englishEpisodes` order (whatever TVDB returned, generally aired order ascending); `.take(policy.maxPerEpisodeTranslationFallbacksPerRequest)` truncates the first 8 missing-localized IDs. If the upstream TVDB response order ever changes (TVDB has historically reordered episodes after metadata edits), the *set of episodes* that get per-episode translation fetches will change run-to-run for a given series. Cache keys are per-episode, so this only changes which 8 of N missing-localized episodes land in the user's cache first — not correctness — but the trace will be non-deterministic across runs.
- **Violated contract:** None directly; reproducibility hygiene.
- **User-visible impact:** None functional. Operator triage of "which episodes did NEXIO try to translate" becomes order-dependent on TVDB response stability.
- **Required fix:** Sort `englishEpisodes.mapNotNull { ... }` by `(seasonNumber, number)` before `.take(...)` to guarantee a stable order.
- **Test or report that should catch it:** Property test asserting that for two permutations of the same `englishEpisodes` list, `idsMissingLocalizedFields` returns the same set.

## Outcome

CHANGES_REQUESTED — Lane E's *contract* is sound. The three core requirements (same-provider English fallback, no cross-provider fallback, English fetches use CacheFirst with policy-versioned keys) are correctly enforced in code by `LocalizationPolicy` (uniform `allowProviderFallbackForMissingLocalizedFields = false`), `LocalizationResolver` (provider filter before priority ranking), and the per-provider adapter fan-out. The blocking items are all on the **on-device verifiability** axis: F-E-02 (no `metadata.localization_plan` emission — helper deleted, no canonical owner), F-E-03 (per-episode field winners invisible to trace), and F-E-01 (per-episode fallback counter computed but discarded). F-E-04 is P2 (Kitsu single-fetch design needs explicit policy marker), F-E-05 is a nit. No production code violates the contract, but production trace cannot prove the contract was followed — which is the audit's primary concern at this phase.
