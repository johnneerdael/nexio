## What changed (per diff map)

The cache/backoff plane is a phase-5 introduction: `IntegrationCacheStore` is the SPI, `LocalIntegrationCacheStore` (in `data/local/integration/`) implements it on top of a Room `IntegrationCacheDao` for metadata + a filesystem `IntegrationBlobStore` for the encoded payload. `IntegrationCachePolicy` is a sealed type (`Disabled`, `ObserveOnly(reason)`, `CacheFirst(ttlMs, staleAfterExpiryMs)`, `Mutation`). `IntegrationBackoffManager` persists per-`(provider, scope)` blocks via `IntegrationProviderBackoffDao`. `IntegrationSingleFlight` coalesces concurrent fetches by `cacheKey` using a `Mutex`-guarded map of `CompletableDeferred`. `MetadataCacheKeys` formats router/document/artwork cache key strings; `ArtworkImageCacheKeys` is the canonical poster/backdrop/logo key builder used across UI surfaces. Cache invalidation is driven exclusively through `deleteOwnedMedia(mediaKey)` from `IntegrationOrphanCleanupService` after rail ownership drains.

## Findings

### F-D-01: 429/5xx in cache-miss path returns Missing instead of falling back to stale

- **Severity:** P1
- **Evidence:** `app/src/main/java/com/nexio/tv/core/integration/DefaultIntegrationRuntime.kt:611-628` (HttpError branch of `executeProviderLoad` registers backoff at `:617-624` then returns `IntegrationFetchResult.Missing` at `:627` without consulting `cacheStore.readStale(spec)`); contrast `:544-557` where the runtime *does* fall back to stale on `IntegrationFetchResult.Missing` from a non-429 path.
- **Violated contract:** Stale-on-429 fallback path returns the stale value AND registers backoff (Lane D Contract 2).
- **User-visible impact:** When TMDB / TVDB / Trakt return 429 in response to a CacheFirst metadata fetch where the entry has *expired fresh* but is *still within stale window*, the caller receives `Missing` instead of `Stale(value)`. UI surfaces (Home rows, MetaDetails enrichment, ContinueWatching localization) flicker to placeholder/empty state for one render cycle even though usable cached data exists. The stale path does fire on the *next* invocation (because `backoffManager.isBlocked` is then true and the stale hit is served at `:497-512`), so the bug is timing-dependent and only the first concurrent caller is affected.
- **Required fix:** In `executeProviderLoad`'s `HttpError` branch (and symmetrically in the `NetworkError` branch at `:629-639`), before returning `IntegrationFetchResult.Missing`, attempt `cacheStore.readStale(spec)` and, when present, return `IntegrationFetchResult.Stale(...)` with a `STALE_HIT` `runtime.cache_decision` carrying `reason = "stale-cache-hit-backoff-inline"`. Note this requires plumbing `spec` and `traceContext` into `executeProviderLoad` (currently only `traceId` is passed) — minor refactor.
- **Test or report that should catch it:** New `DefaultIntegrationRuntimeStaleOn429Test`: seed a stale (expired-fresh, still-stale) cache entry, stub the loader to return `IntegrationLoadResult.HttpError(429, retryAfterMs = 12_000)`, assert (a) result is `Stale(seeded)` not `Missing`, (b) `backoffManager.isBlocked` becomes true, (c) a `STALE_HIT` cache_decision was emitted with `networkSuppressed = false`. Also extends F-TM-01 coverage.

### F-D-02: Cache write is non-atomic — blob and Room row updated separately

- **Severity:** P1
- **Evidence:** `app/src/main/java/com/nexio/tv/data/local/integration/LocalIntegrationCacheStore.kt:54-67` — `file.writeBytes(...)` runs at `:54` (truncate-then-write, not `tmp+rename`), then `cacheDao.upsertCacheEntry(...)` runs at `:55-67`. No `@Transaction`, no atomic rename, no fsync barrier. `IntegrationCacheDao.kt:11` is a single `@Insert(REPLACE)`. `singleFlight` (`DefaultIntegrationRuntime.kt:482`) coalesces fetches that share the same `cacheKey`, but a *different* in-flight reader that already passed the `singleFlight.run` boundary (e.g., the second invocation that re-enters `readFresh` at `:483` after the first writer started its `cacheStore.write` at `:528`) can observe a torn state.
- **Violated contract:** Cache writes are atomic and don't race with reads (Lane D Contract 3).
- **User-visible impact:** On Android `Context.filesDir` (a normal ext4 mount), `file.writeBytes` is implemented as `FileOutputStream(file).use { it.write(bytes) }` — the file is truncated to zero, then bytes are streamed. A reader running between truncate and final flush will read 0 bytes (or N partial bytes) and `spec.codec.decode` will throw or yield garbage. The Room `expiresAtEpochMs` is also still pointing at the *old* `freshUntil` until the `upsertCacheEntry` line completes, so a reader seeing old DB metadata + new partial blob is plausible. In practice the window is microseconds, but on rapid consecutive invalidations or concurrent `getInternal` paths bypassing single-flight (see F-A-02), the race is reachable.
- **Required fix:** (a) Write blob to `${blobPath}.tmp` then `File.renameTo(${blobPath})` — POSIX rename is atomic for same-volume targets; (b) wrap the file rename + DAO upsert in a Room `@Transaction suspend fun upsertCacheEntryAndPath(...)` so DB visibility is synchronous with file visibility from the reader's perspective; (c) document that `readFresh` MUST tolerate `FileNotFoundException` on the blob path and return `null` (currently `:24` returns `null` only on `!file.exists()` — a partial write where the file *does* exist but the bytes are short will surface as a codec exception).
- **Test or report that should catch it:** New `LocalIntegrationCacheStoreAtomicityTest` (Robolectric/coroutine): two parallel coroutines, one calling `write(spec, valueA)` repeatedly, the other calling `readFresh(spec)` in a tight loop; assert no read ever throws and every successful read returns either `null` or a decoded `valueA` — never a partial/corrupted decode. Also add an audit assertion that `IntegrationCacheDao` is invoked from a Room `@Transaction` wrapper.

### F-D-03: `INVALIDATED` and `EVICTED` cache-decision values are dead

- **Severity:** P2
- **Evidence:** `app/src/main/java/com/nexio/tv/core/trace/TraceCacheDecision.kt:11-12` declares `INVALIDATED, EVICTED`. Grep across the worktree finds zero production emissions: `DefaultIntegrationRuntime.kt` only uses `HIT, MISS_THEN_NETWORK, STALE_HIT, EXPIRED_MISS, BYPASS_DISABLED, OBSERVE_ONLY, WRITE` (lines 178–562). `IntegrationOrphanCleanupService.cleanupIfOrphaned` (`:12-16`) and `LocalIntegrationCacheStore.deleteOwnedMedia` (`:70-76`) delete blob + Room rows but never emit through `RuntimeTraceSink`. Mirrors F-A-03 (Noop sink suppression) for the orthogonal case where the emit site itself is missing.
- **Violated contract:** Cache invalidation paths emit `INVALIDATED` / `EVICTED` `runtime.cache_decision` (Lane D Contract 4).
- **User-visible impact:** Audit / trace consumers cannot distinguish a "cache row deleted because owning media was orphaned" event from a normal cache miss. CI rules that gate on `EVICTED` to detect runaway invalidation storms have nothing to count. The trace JSONL is silent during cleanup, masking pruning-related performance regressions (e.g., a bug in `cleanupAll` that deletes more than expected).
- **Required fix:** Either (a) add an `IntegrationCacheStore.delete(cacheKey, reason)` overload that goes through `RuntimeTraceSink` and emits `EVICTED` (with `reason = "orphan-cleanup"`); have `IntegrationOrphanCleanupService` call this. Add a corresponding `INVALIDATED` emit when a write is overwritten (currently `WRITE` is the only signal). Or (b) drop `INVALIDATED, EVICTED` from `TraceCacheDecision` and document the limited-decision design in the audit. Recommend (a): the schema is more useful than the partial implementation.
- **Test or report that should catch it:** Architecture/golden test asserting every value of `TraceCacheDecision` is emitted from at least one production code path (similar to "every IntegrationAuditPhase emitted"). Plus a `IntegrationOrphanCleanupServiceTraceTest` asserting `EVICTED` rows in the trace after `cleanupIfOrphaned` succeeds.

### F-D-04: `MetadataCacheKeys.localized` is unused — providers build localized keys ad-hoc

- **Severity:** P2
- **Evidence:** `app/src/main/java/com/nexio/tv/core/metadata/router/MetadataCacheKeys.kt` is the only declaration; grep `MetadataCacheKeys` across `app/src` returns one production file (the declaration) and one test (`MetadataCacheKeysTest.kt`). No provider integration calls `.localized(...)`. Localized text cache keys for TVDB / TMDB / Kitsu localized shapes are built inline inside the provider adapters (referenced from Lane E findings on localization policy, file paths under `data/integration/metadata/**`).
- **Violated contract:** Localized text cache keys include `lang:` AND `policy:vN` (Lane D Contract 6) — structurally satisfiable but not centrally enforced.
- **User-visible impact:** When a future localization-policy version bump lands (e.g., TVDB switches to a new translation merge order), each provider adapter must remember to bump its inline `policy:vN` literal independently. Forgetting one provider silently serves the *previous* policy's cached payload as if it were the current one — wrong overview text in the user's locale until manual cache wipe. Reviewers cannot grep a single helper to verify the bump was applied uniformly.
- **Required fix:** Migrate provider-side localized cache key builders to call `MetadataCacheKeys.localized(...)`. Add a unit test for each provider that the cache key contains `:lang:<expected>` and `:policy:<expected-version>`. Alternatively, if the helper truly is dead, delete it (and `MetadataCacheKeysTest`) and document the per-provider key conventions in `02-architecture-boundary-map.md`. Lane E owns the localized text policies — coordinate the migration with F-TM-06.
- **Test or report that should catch it:** Architecture rule scanning provider adapter sources for the literal substrings `lang:` and `policy:` near `cacheKey =` declarations; plus a fold-in test that the resolved cache key for each `LocalizationPolicy` version matches `MetadataCacheKeys.localized(...)` byte-for-byte.

### F-D-05: Single-flight key map can leak typed casts on coincidental key collision

- **Severity:** Nit
- **Evidence:** `app/src/main/java/com/nexio/tv/core/integration/IntegrationSingleFlight.kt:12,19-22,38` — the `inFlight` map is keyed by `cacheKey: String` and values are `CompletableDeferred<IntegrationFetchResult<*>>`. The unchecked cast at `:20` and `:38` (`as? CompletableDeferred<IntegrationFetchResult<T>>`) trusts that two different specs cannot share a `cacheKey`. Cache key construction *should* uniquely identify the value type (provider + apiShape + operationKey + scope), but if two specs accidentally collide (e.g., a future refactor that drops `apiShapeId` from `MetadataCacheKeys.providerMetadataKey`), the second caller will receive a `CompletableDeferred<IntegrationFetchResult<WrongType>>` and `ClassCastException` will surface as a coroutine crash deep inside the consumer — not at the `singleFlight.run` boundary.
- **Violated contract:** None directly; type-safety hygiene.
- **User-visible impact:** A latent bug class. Today none of the cache-key formatters collide (verified by grep over all `IntegrationKeyFactory.build` and inline keys), but the cast site has no fail-fast.
- **Required fix:** Either (a) include a `KClass<T>` token in the inFlight map and assert on rejoin, or (b) widen the key to `(cacheKey, valueType)`. Option (b) is cheaper and correct.
- **Test or report that should catch it:** Property test that constructs two specs with identical `cacheKey` and different `T`, races them, and asserts the runtime fails fast (rather than crashing in the consumer).

### F-D-06: `IntegrationBackoffManager` has no exponential schedule, no clear-on-success (cross-ref F-TM-01)

- **Severity:** P2 (re-stated from test matrix)
- **Evidence:** `app/src/main/java/com/nexio/tv/core/integration/IntegrationBackoffManager.kt:19` — `blockMs = retryAfterMs ?: if (statusCode == 429) 2_000L else 5_000L`. There is no growth term (consecutive 429s reset the same 2s window), no jitter, and no successful-call clear. Once a block is set it persists in Room for `blockMs` regardless of any subsequent successful calls. `IntegrationProviderBackoffEntity` carries no `consecutiveFailures` counter.
- **Violated contract:** 429/5xx triggers backoff (test matrix Contract 3, partial).
- **User-visible impact:** A provider that flaps (success → 429 → success → 429) will spend the full 2s/5s blocked window on every 429 even though it just succeeded. Conversely, a long-running rate-limit (e.g., TMDB hourly quota exhaustion) is treated identically to a transient 429 and unblocks after 5s, immediately re-hammering the upstream and re-tripping the limit. No clear-on-success means an explicitly-cleared `Retry-After: 0` cannot unblock the provider mid-window.
- **Required fix:** Add (a) exponential backoff with cap (e.g., `2s → 4s → 8s → 30s` capped at 5min, jitter ±10%), tracked via `consecutiveFailures` on the entity; (b) explicit `clear(provider, scope)` invoked from `executeProviderLoad` on `IntegrationLoadResult.Success`; (c) honor an explicit zero `Retry-After`.
- **Test or report that should catch it:** Extend `IntegrationBackoffManagerTest` with: 5xx escalation, exponential growth, jitter bounds, clear-on-success, and zero-Retry-After honored.
