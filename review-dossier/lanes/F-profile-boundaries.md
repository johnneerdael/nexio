## What changed (per diff map)

(1) `IntegrationSpec.init` (`IntegrationSpec.kt:24`), `IntegrationCallSpec.init` (`IntegrationCallSpec.kt:17`), and `IntegrationStreamSpec.init` (`IntegrationStreamSpec.kt:17`) all call `ProfileBoundaryEnforcer.validateRequest(provider, scope, cacheKey/operationKey, profileContext)` so any spec instance that survives construction has been audited. (3) `ProfileManager.setActiveProfile(id)` (`:109-125`) now reads the profile list from `dataStore.profilesList.first()`, no-ops when `_activeProfileId.value == id`, and throws `ProfileBoundaryException(PROFILE_SWITCH_BLOCKED_BY_ACTIVE_PLAYBACK)` whenever `playbackSessionRegistry.activeOwner() != null`; the `init { dataStore.activeProfileId.collect ... }` reactive path silently ignores the same condition (`Log.w` then `return@collect`). (4) Per-profile durable storage: `ProfileDataStoreFactory.get(profileId, featureName)` returns a `DataStore<Preferences>` whose file name is suffixed with `_p${profileId}` for non-primary profiles (primary = unsuffixed for migration compat); `TraktAuthDataStore` and `SimklAuthDataStore` route every read/write through `factory.get(profileId, FEATURE)` keyed off `profileManager.activeProfileId.value`. ## Findings

### F-F-01: UI callers of `setActiveProfile` don't catch `ProfileBoundaryException` — crash risk during active playback (Path 10, P1)

- **Severity:** P1
- **Evidence:** Three production call sites of `ProfileManager.setActiveProfile`:
  - `MainActivity.kt:343-352` — `switchProfileAndApplyLocale(profileId)` invokes `lifecycleScope.launch { ... profileManager.setActiveProfile(profileId) ... }`. No try/catch around the call.
  - `MainActivity.kt:518-534` — `ProfileSelectionScreen(onProfileSelected = { profileId -> profileSelectionScope.launch { ... profileManager.setActiveProfile(profileId) ... } })`. No try/catch.
  - `ProfileSelectionViewModel.kt:47-51` — `fun selectProfile(profileId: Int) { viewModelScope.launch { profileManager.setActiveProfile(profileId) } }`. No try/catch.
  - `grep -rn "catch.*ProfileBoundary" app/src/main` returns exactly one hit — `ContinueWatchingSnapshotService.kt:1057`, which catches the *stale-write* variant in `canPublishProfileWrite`, NOT the switch-during-playback variant in `setActiveProfile`.
  - `ProfileBoundaryException extends IllegalArgumentException` (`ProfileBoundaryViolation.kt:18-21`), an unchecked subclass that propagates out of the coroutine.
- **Violated contract:** Lane F Contract 5 — the rejection path is structurally sound but the calling integration is not safe. UI code must either swallow + show a toast or never invoke `setActiveProfile` while playback is active.
- **User-visible impact:** A user who opens the profile picker overlay (e.g., long-press menu) while a movie is playing — a legitimate Android-TV gesture — and selects a different profile will trigger `setActiveProfile`, which will throw `PROFILE_SWITCH_BLOCKED_BY_ACTIVE_PLAYBACK`. In `lifecycleScope.launch { ... }` and `viewModelScope.launch { ... }` an uncaught exception triggers the parent scope's `CoroutineExceptionHandler`. For `viewModelScope` and `lifecycleScope` (no custom handler installed in `MainActivity`/`ProfileSelectionViewModel`), the default behavior on Android is to re-throw to the global `Thread.UncaughtExceptionHandler`, which crashes the app with `IllegalArgumentException: Cannot switch profile while playback owned by ...`. At minimum the launch silently cancels and the UI shows no error — the user clicks the profile and nothing happens; no toast, no PIN prompt, no playback stop.
- **Required fix:** Wrap each `setActiveProfile` call in `try { ... } catch (e: ProfileBoundaryException) { ... }`, surface either a "Stop playback first" toast (`PROFILE_SWITCH_BLOCKED_BY_ACTIVE_PLAYBACK`) or a generic boundary message. Better: introduce a `ProfileSwitchResult` sealed class returned from `setActiveProfile` — `Success | RejectedActivePlayback(owner)` — so the type system forces callers to handle the rejection. Tests: `ProfileSelectionViewModelSwitchDuringPlaybackTest` asserting that selecting a profile while a fake playback owner is registered emits a `_uiEvent.emit(ShowSwitchBlockedToast(...))` instead of letting the exception escape.
- **Test or report that should catch it:** Existing `ProfileSwitchDuringPlaybackTest` covers the *enforcer* throwing; missing is an integration test that exercises `ProfileSelectionViewModel.selectProfile` with an active playback owner and asserts no uncaught exception.

### F-F-02: Profile-switch rejection short-circuits before enforcer, so no `profile.boundary_check` trace event fires (Path 10, P2)

- **Severity:** P2
- **Evidence:** `ProfileManager.kt:113-119` constructs the `ProfileBoundaryException` inline:
  ```
  val owner = playbackSessionRegistry.activeOwner()
  if (owner != null) {
      throw ProfileBoundaryException(
          ProfileBoundaryViolation.PROFILE_SWITCH_BLOCKED_BY_ACTIVE_PLAYBACK,
          "Cannot switch profile while playback owned by ..."
      )
  }
  ```
  This bypasses `ProfileBoundaryEnforcer.validateRequest` entirely — the enforcer is the only emitter of `profile.boundary_check` trace events (`ProfileBoundaryEnforcer.kt:67-77, 82-124`). `grep -rn "profile.boundary_check\|emitBoundaryCheck" app/src/main/java` returns three hits, all inside `ProfileBoundaryEnforcer.kt`. There is no `traceSink.emit(... eventType = "profile.boundary_check" ...)` call in `ProfileManager.kt` or anywhere else.
- **Violated contract:** None hard-violated — the rejection itself is correct (Contract 5 PASS). What's violated is the trace observability axiom that any boundary verdict (PASS or FAIL) should be observable in `profile.boundary_check`. Cross-ref to Lane I (trace mode) Contract: every boundary decision must be visible in trace bundles.
- **User-visible impact:** When a user reports "I tried to switch profiles during playback and the app crashed/did nothing", the trace bundle uploaded from the device will contain zero `profile.boundary_check` events tagged `verdict = "FAIL"` with `violation = "PROFILE_SWITCH_BLOCKED_BY_ACTIVE_PLAYBACK"`. The operator must infer the cause from the absence of expected events plus the crash log. With trace coverage, the bundle would carry the rejected switch, the active owner's `profileHash`, and the timestamp.
- **Required fix:** Two options. (a) Move the playback check into `ProfileBoundaryEnforcer` as a new entry point — e.g., `ProfileBoundaryEnforcer.assertCanSwitchProfile(targetProfileId, registry)` — that wraps the check in the same try/`emitBoundaryCheck` pattern used by `validateRequest`. The `scope` payload field would need a synthetic `ProfileSwitch` audit name (or a new event type `profile.switch_check`). (b) Inline a `traceSink.emit(...)` in `ProfileManager` — cheaper but duplicates the boundary-event shape.
- **Test or report that should catch it:** Trace validator rule: every `ProfileBoundaryException` instance constructed in production must have a corresponding `profile.boundary_check` (or sibling) trace event in the same `traceSessionId` within ±10ms. Test: `ProfileSwitchDuringPlaybackTraceTest` — register a fake playback owner, install a capturing `RuntimeTraceSink`, call `setActiveProfile`, assert the captured envelopes contain the FAIL event.

### F-F-03: `ProfileMetadataOverlay` defined but unused in production (boundary map Q4)

- **Severity:** P2
- **Evidence:** `ProfileMetadataOverlay.kt:5-17` defines a typed overlay with `profileId`, `watched`, `progress`, `listMembership`, `scrobbleState`, `userRating`, `continueWatching`. `ProfileResolvedDisplayDocument.kt:3-11` defines a wrapper with the overlay and asserts `profileId == overlay.profileId`. `grep -rn "ProfileMetadataOverlay\|ProfileResolvedDisplayDocument" app/src/main` returns only the two definition sites and *zero* consumer call sites — no router, no provider, no UI binder, no DI wiring constructs either type. The only test reference is `CompositionTypeShapeTest:20-26`, a reflection-based shape test that the field set hasn't drifted, but the type is never instantiated against real data.
- **Violated contract:** None directly — this is dead code surface, not a profile-boundary correctness violation. However, the existence of an unused typed overlay implies that profile-bound metadata composition (CW + watched + scrobble + ratings) is currently routed through *untyped* maps or per-call ad-hoc structs (e.g., directly stitched in the UI binders). That untyped routing is harder to audit for boundary leaks (no `require(profileId > 0)` invariant when fields are spread across loose parameters).
- **User-visible impact:** None today — the unused type doesn't ship as a payload. The latent risk is during the planned refactor: a future PR that wires `ProfileMetadataOverlay` into the router must thread the `profileId` invariant through every adapter, and missing one site will silently downgrade to untyped composition without a compile error (because the existing untyped path will continue to work).
- **Required fix:** Either (a) wire `ProfileMetadataOverlay` as the single output type of profile-overlay composition (one site that produces an overlay per `(contentId, profileId)` tuple, with `ProfileResolvedDisplayDocument.profileId == overlay.profileId` enforced at construction — the `require` already exists); or (b) delete the unused types and document the deferral. Option (a) is preferred per the boundary-map plan (Q4 deferred refactor); option (b) is the cheap path if the refactor slips.
- **Test or report that should catch it:** A "dead types" report in the audit dossier should list `ProfileMetadataOverlay` and `ProfileResolvedDisplayDocument` until they reach a runtime construction site. Lane J (legacy deletion) should pick this up if it survives one more cycle without consumers.

### F-F-04: Reactive `dataStore.activeProfileId.collect` silently ignores switch during playback (no exception, no trace)

- **Severity:** P2
- **Evidence:** `ProfileManager.kt:84-101`:
  ```
  init {
      scope.launch {
          dataStore.activeProfileId.collect { id ->
              val previousId = _activeProfileId.value
              if (previousId != id && playbackSessionRegistry.activeOwner() != null) {
                  Log.w(TAG, "Ignoring DataStore profile change to $id while playback active")
                  return@collect
              }
              ...
          }
      }
  }
  ```
  Compare with the imperative `setActiveProfile(id)` path which throws `ProfileBoundaryException` for the same condition. The reactive path does not throw, does not emit a trace event, and does not retry — the `_activeProfileId` StateFlow remains on the previous value while the underlying `dataStore.activeProfileId` Flow has emitted the new value. On the next active-profile collection (e.g., after playback ends and the DataStore re-emits the same value? — it won't, because Flow distinct semantics suppress duplicate emissions in some configurations), the divergence persists. The DataStore-vs-StateFlow split is observable to any reader that reads the DataStore directly (e.g., `ProfileDataStoreImpl.activeProfileId.first()`).
- **Violated contract:** Lane F Contract 5 (asymmetric — imperative path enforces with exception, reactive path enforces with silent log). Cross-ref Lane A (runtime control plane) Contract on state convergence.
- **User-visible impact:** Two scenarios. (1) The user is watching content on profile 1, walks to a different room, and a sync from a sibling device pushes the active profile to profile 2 via Postgres → `ProfileSyncService` → `dataStore.setActiveProfile(2)`. The local app silently stays on profile 1. When playback ends, the StateFlow has not been re-collected because the DataStore Flow already emitted (and was suppressed). The user's profile context appears to spontaneously revert to profile 1's library/CW after they expect profile 2. (2) The reactive path is the source of truth for `AppLocaleResolver.setActiveProfileId`, so the locale also fails to update. Re-launching the app reads from DataStore (now profile 2) and corrects, so this is "self-healing" but transiently broken.
- **Required fix:** Either (a) make the reactive path throw the same exception (and let the parent `scope.launch` handle it via a `CoroutineExceptionHandler` that schedules a retry after `playbackSessionRegistry` becomes idle), or (b) explicitly defer the change: enqueue `id` as a `pendingActiveProfileId`, register a `playbackSessionRegistry` idle callback that drains the pending switch when playback ends. Option (b) is the correct UX — the user's expressed intent (switch profile from another device) is honored as soon as safe. Add a `profile.boundary_check` trace event for the deferral so operators can see it.
- **Test or report that should catch it:** `ProfileManagerReactiveSwitchDuringPlaybackTest`: register a playback owner, push a new active id through the DataStore, assert that on playback end the StateFlow converges to the new id. Currently no such test exists (`grep -rn "Ignoring DataStore profile change"` returns only the production code).

### F-F-05: `ProfileBoundaryEnforcer.validateLegacyAccountScope` is a partial guard — only blocks `profile:` substring, not credential leakage

- **Severity:** Nit
- **Evidence:** `ProfileBoundaryEnforcer.kt:263-271`:
  ```
  private fun validateLegacyAccountScope(cacheKey: String?) {
      val key = cacheKey.orEmpty()
      if (key.contains("profile:")) {
          throw ProfileBoundaryException(
              ProfileBoundaryViolation.ACCOUNT_SCOPE_CONTEXT_MISSING_ACCOUNT,
              "Legacy account scope cannot be used for profile-bound cache key: $key"
          )
      }
  }
  ```
  The legacy `Account(providerAccountId)` constructor (`IntegrationScope.kt:86-100`, marked `@Deprecated(level = ERROR)`) is the only producer of legacy-shape `Account` scopes. The legacy guard checks for `profile:` substring but doesn't validate the cache key includes `account:` or any credential-binding token. A caller who passes a key like `"trakt:libraries:movies"` would pass this check despite the scope being notionally account-bound.
- **Violated contract:** None — the deprecated-ERROR annotation means new code can't construct legacy-shape `Account` instances. The fragility is purely historical.
- **User-visible impact:** None — no current code path constructs the legacy shape (the `@Deprecated(level = ERROR)` is a compile-time block).
- **Required fix:** Delete the legacy `Account(providerAccountId)` constructor entirely and remove the `validateLegacyAccountScope` branch. Since the deprecation level is `ERROR`, no production code can call it; this is a Lane J (legacy deletion) candidate.
- **Test or report that should catch it:** `IntegrationScopeAccountLegacyConstructorTest` already exists in spirit through the `@Deprecated(level = ERROR)`. The cleanup is a J item.

## Outcome

CHANGES_REQUESTED — Lane F's *contracts* are sound at the enforcer level. The five core requirements that are testable at construction time (1: every spec validates, 2: profile scopes need context, 3: account scopes need credential match, 4: authenticated providers can't go global, 7: tokens are profile-keyed) all PASS with strong evidence. Outbox profile binding (Contract 6) is also sound — every envelope carries `profileId`, persistence is per-profile-prefs, and the coordinator runs one isolated drain loop per profile. The blocking items cluster on the **profile-switch rejection** axis: F-F-01 (UI callers crash or silently swallow on rejection — Path 10 P1), F-F-02 (rejection bypasses the enforcer's trace emission — Path 10 P2), and F-F-04 (the reactive `dataStore.activeProfileId.collect` path silently ignores the same condition rather than enforcing it). F-F-03 is a P2 dead-type cleanup (boundary-map Q4 deferred). F-F-05 is a Nit and a Lane J candidate. No production code violates the boundary, but the boundary's enforcement of `setActiveProfile` is one-and-a-half layers (imperative throws but uncaught; reactive logs and ignores) instead of a uniform "every rejection produces a typed error AND a trace event" guarantee.
