## Findings

### F-H-01 (cross-ref F-TM-08): No architecture pin asserting `checkin()` retains the `ownerProfileId: Int? = null` shape

- **Severity:** P3
- **Evidence:**
  - `TrackingScrobbleService.checkin(item, message?, ownerProfileId: Int? = null): Boolean` (`TrackingScrobbleService.kt:41`) is intentionally distinct from the lifecycle scrobble surface, which all take `owner: PlaybackOwnerContext` (`:38-40`). The asymmetry is real: `checkin` is invoked from non-playback Trakt/Simkl mark-watched flows where the caller has no `PlaybackSessionRegistry` token / `PlaybackOwnerContext` to materialize.
  - `find app/src/test/java/com/nexio/tv/architecture -type f -name "*.kt"` enumerates `ArchitectureScan.kt`, `IntegrationBoundaryTest.kt`, `MetadataProductionBoundaryTest.kt`, `MetadataRouterBoundaryTest.kt`, `NoDirectAuthServiceUsageOutsideIntegrationBoundaryTest.kt`, `NoIntegrationRuntimeInjectionOutsideBoundaryTest.kt`, `ProfileBoundaryArchitectureTest.kt`. None of them assert anything about `TrackingScrobbleService.checkin`'s signature.
  - `grep -rn "checkin" app/src/test/java/com/nexio/tv/architecture` returns zero hits. The closest coverage is the behavioral test `DefaultTrackingScrobbleServiceTest.kt:45-167` exercising routing — but a behavioral test would still pass if `checkin` were migrated to take `PlaybackOwnerContext` (the test would just have to construct one).
  - The diff map H-Q6.1 candidate flags this as a "boundary map" item: `nullable ownerProfileId defaults on Trakt/Simkl underlying services` (`TraktScrobbleService.kt:102,117,132,147`, `SimklScrobbleService.kt:77,92,107,122` all keep `ownerProfileId: Int? = null`). The default values are unused by `DefaultTrackingScrobbleService` (which always passes `owner.ownerProfileId` explicitly), so they exist purely for the `checkin` shape and for the (non-`PlaybackOwnerContext`) test stubs.
- **Violated contract:** Lane H Contract 2 holds today, but there is no automated guard preventing regression. F-TM-08 in the test matrix is unresolved.
- **User-visible impact:** None. Operator/developer impact: a future "harmonize the scrobble surface" refactor that migrates `checkin` to `PlaybackOwnerContext` would compile, pass all existing tests, but would force every checkin call site (which today has only an `Int?`) to fabricate a `PlaybackOwnerContext` with `ownerSessionId = ""`, `traktAccount = null`, `simklAccount = null`, `startedAtEpochMs = ?` — a fabricated playback session that never existed. Worse, if `assertCanWriteProfileState` is later wired into the lifecycle path (per F-H-03), the fabricated session would either falsely pass or falsely fail the boundary check.
- **Required fix:** Add an architecture-pin test `TrackingScrobbleServiceCheckinShapeTest` (under `app/src/test/java/com/nexio/tv/architecture/`) that uses reflection to assert the `checkin` `KFunction`'s parameter types are exactly `[TrackingScrobbleItem, String?, Int?]` and that the third parameter has a default value. Document the asymmetry rationale in the `TrackingScrobbleService` interface KDoc: "`checkin` retains the nullable `Int?` form because it is invoked outside the `PlaybackSessionRegistry`-tracked playback lifecycle".
- **Test or report that should catch it:** Architecture pin test as above. Update F-TM-08 in `08-test-matrix.md` to point at the new pin.

### F-H-02: `PlaybackSessionRegistry` is single-slot — concurrent `PlayerViewModel`s would silently overwrite each other's registration

- **Severity:** P3
- **Evidence:**
  - `PlaybackSessionRegistry.kt:9-29` holds a single `AtomicReference<Entry?>` keyed on a `(token, context)` pair. `register(context)` (`:14-18`) builds a fresh UUID token and calls `current.set(Entry(token, context))` — *always overwriting* whatever was previously registered.
  - `unregister(token)` (`:20-24`) uses `updateAndGet { existing -> if (existing != null && existing.token == token) null else existing }` — correctly preserves a *newer* registration when an older token's `unregister` arrives, but the older entry has already been silently overwritten by the time the newer `register` ran.
  - `PlayerViewModel.kt:78` runs the `register(...)` call eagerly in the controller-init `run` block. The unregister symmetry (`:127, 168`) only fires on `stopAndRelease()` and `onCleared()` — not on a *newer* VM's construction.
  - Concurrency scenario: navigate to `/player` for stream A, immediately (before `onCleared` runs for VM A) navigate-replace to `/player` for stream B. VM B's `init` calls `register(contextB)` and `current.set(Entry(tokenB, contextB))` — VM A's entry is gone from the registry but VM A is *still alive* (its `viewModelScope` may still be running scrobble-heartbeat coroutines per `PlayerRuntimeControllerPlaybackEvents.kt:405-417`). Any later consumer of `activeOwner()` (`PlaybackSessionRegistry.kt:26`) sees VM B's owner while VM A is still emitting scrobble traffic.
  - `grep -rn "activeOwner()\|isIdle()" app/src/main/java` returns zero callers today — the registry is *write-only* in production. Every consumer reads the owner from a directly-injected `PlaybackOwnerContext`, not from the registry. So today the single-slot limitation has no observable effect.
- **Violated contract:** Lane H Contract 4 holds for the *single-VM* case but does not state behavior under concurrent VMs. The registry is documented as "active session tracking" but cannot represent multiple sessions and has no read consumers to surface the shadowing.
- **User-visible impact:** None today. Latent: if a future feature consumes `activeOwner()` (e.g., a "currently watching" widget, or a `STALE_SESSION_WRITE_REJECTED` rule per F-H-03 that compares owner-context to the registry's active entry), the comparison would silently use the most-recent VM's context — and a stale VM A scrobble would either falsely pass (if A == B's profile) or falsely fail (if A != B's profile) the check.
- **Required fix:** Either (a) document the single-slot constraint in the class KDoc and add an architecture-pin test that there is at most one `PlayerViewModel` instance live at a time (e.g., via a Hilt-scoped `@PlayerSession` qualifier or a `viewModelStore` audit); or (b) replace the `AtomicReference<Entry?>` with a `ConcurrentHashMap<String, PlaybackOwnerContext>` so concurrent registrations coexist, and have `activeOwner()` return the *most recent* by `startedAtEpochMs` (so a stale leftover does not shadow a newer session). Option (b) is also a prerequisite for any future "list active playback sessions" UX.
- **Test or report that should catch it:** Add `PlaybackSessionRegistryConcurrentRegistrationTest` that registers two contexts in sequence and asserts: (after register A) `activeOwner() == contextA`; (after register B) `activeOwner() == contextB`; (after unregister A's stale token) `activeOwner() == contextB` (already passes today); (after unregister B) `activeOwner() == null`. Also add a test asserting the documented behavior under option (a) or (b) once chosen.

### F-H-03 (cross-ref Path 11): No result-time `assertCanWriteProfileState` re-check on scrobble completion — `STALE_SESSION_WRITE_REJECTED` is unreachable from the scrobble path

- **Severity:** P1
- **Evidence:**
  - The contract requires that a scrobble queued under profile A but completing after a switch to profile B should be rejected via `assertCanWriteProfileState` and emit `STALE_SESSION_WRITE_REJECTED`. `grep -rn "assertCanWriteProfileState" app/src/main/java` returns: `core/integration/ProfileBoundaryEnforcer.kt:126,140,144` (decls) and `data/repository/ContinueWatchingSnapshotService.kt:1052` (the CW-write call site). **No scrobble service invokes the helper.**
  - `grep -rn "STALE_SESSION_WRITE_REJECTED" app/src/main/java` returns hits in `core/trace/TraceValidationRules.kt`, `core/integration/ProfileBoundaryEnforcer.kt`, `core/integration/ProfileBoundaryViolation.kt`, `core/profile/ProfileManager.kt`, `data/repository/ContinueWatchingSnapshotService.kt`, `ui/screens/player/PlayerViewModel.kt` — but a closer inspection shows the scrobble-side site does not exist (`grep "STALE_SESSION_WRITE_REJECTED" app/src/main/java/com/nexio/tv/data/repository/T*Scrobble*.kt` and `*data/trakt/outbox/*` returns zero hits).
  - Trace through the scrobble request -> result chain:
    - `PlayerRuntimeControllerPlaybackEvents.kt:323-332` launches the scrobble in `scope` (= `viewModelScope`). The call passes `owner = playbackOwnerContext`, captured at controller construction time from `profileManager.activeProfileSession.value` (`PlayerViewModel.kt:69-77`).
    - `DefaultTrackingScrobbleService.scrobbleStart` (`TrackingScrobbleService.kt:53-65`) reads `providerState(owner)` *once* at request time and routes to `TraktScrobbleService.scrobbleStart(item, progressPercent, owner.ownerProfileId)` (`:62`).
    - `TraktScrobbleService.scrobbleStart` (`:102-115`) resolves `authSession(ownerProfileId)` (`:169-171`: forces `TrackingProvider.TRAKT, ownerProfileId` regardless of current active provider) and calls `submitMutation(WatchingMutationRequest.Scrobble(..., profileId = session.profileId))` (`:107-114`).
    - `submitMutation` (`:173-203`) enqueues via `mutationScope.launch { drainPendingMutations(request.profileId) }` (`:197-200`). `mutationScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)` (`:96`) — this scope outlives `viewModelScope`, so even after VM teardown the drain may complete.
    - `drainPendingMutations` -> `executeMutation` -> `enqueueScrobble` (`:254-283`) finally calls `traktMutationOutboxCoordinator.enqueueAndDrain(envelope)` (`:262-272`). `grep "profileBoundary\|profileManager\|assertCanWrite" app/src/main/java/com/nexio/tv/data/trakt/outbox/ProviderMutationOutboxCoordinator.kt` returns nothing — the outbox is profile-agnostic.
  - At every step, the *intended* `ownerProfileId` is preserved end-to-end (good: the scrobble posts against the original profile's account), but no checkpoint compares "intended profile" vs "currently active profile" and rejects with `STALE_SESSION_WRITE_REJECTED`.
  - Compare with `ContinueWatchingSnapshotService.kt:1052` where the canonical pattern is implemented: the CW write computes a `resultSession`, calls `ProfileBoundaryEnforcer.assertCanWriteProfileState(...)` against the *current* active profile, and on mismatch emits `STALE_SESSION_WRITE_REJECTED` and returns without writing.
- **Violated contract:** Lane H Contract 6.
- **User-visible impact:** None for the user (the scrobble correctly posts against the original profile's account regardless of the switch — this is arguably the *correct* behavior for "I started watching as profile A, finish the scrobble as profile A"). Operator/observability impact: trace bundles do not record that a scrobble *would have been* a stale-session write, so an operator triaging "why is profile B's account seeing scrobbles for content profile A was watching?" has no `STALE_SESSION_WRITE_REJECTED` events to inspect — they have to reconstruct the timeline from `playback.scrobble_request` and `profile.switch` events. More importantly, the architectural intent ("every cross-profile write goes through `assertCanWriteProfileState`") is unenforced for the scrobble surface, so a future change that makes scrobble posting depend on the *current* (not original) profile (e.g., "only scrobble if user is still under profile A") would have no boundary helper to call.
- **Required fix:** At the `ProviderMutationOutboxCoordinator.enqueueAndDrain(envelope)` boundary (or alternatively at the start of `enqueueScrobble`/`enqueueCheckin`), call `ProfileBoundaryEnforcer.assertCanWriteProfileState(expectedProfileId = envelope.profileId, actualProfileId = profileManager.activeProfileId.value, operation = "scrobble.${envelope.action}")`. On `BoundaryViolation`, emit `playback.scrobble_rejected` (with `reason = "STALE_SESSION_WRITE_REJECTED", expectedProfileId, actualProfileId, scrobbleAction`) and either (a) reject the mutation and roll back the optimistic watching-now state via the existing `watchingNowStateController.rollbackIfCurrent(...)` path (`TraktScrobbleService.kt:218-221`), or (b) document the policy explicitly: "scrobble always posts to the originally-intended profile; the violation is informational only". If (b), still emit the rejection trace event so operator dashboards can see the cross-profile drift count.
- **Test or report that should catch it:** Add `TraktScrobbleServiceProfileBoundaryTest` and `SimklScrobbleServiceProfileBoundaryTest`: queue a scrobble under profile id 1, switch the active profile to 2 via the test `ProfileManager` fake, drive the drain, assert that `STALE_SESSION_WRITE_REJECTED` is emitted (option a) or that the mutation completes against profile 1 with an informational rejection trace (option b). Add a `TraceValidationRules` rule that every scrobble request should be paired with either a `playback.scrobble_completed` or a `playback.scrobble_rejected` event.
