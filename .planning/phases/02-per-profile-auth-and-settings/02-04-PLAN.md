**B) Add profile-switch push-suppression guard to AccountSettingsSyncService.kt:**

This addresses Pitfall 3 from RESEARCH: after a profile switch, all 6+ migrated stores emit their new profile's data via `flatMapLatest`. The sync service's observer sees these as "settings changed" and would push the new profile's data — potentially overwriting the old profile's remote data.

Add to AccountSettingsSyncService constructor parameter list:
```kotlin
private val profileManager: ProfileManager,
```

Add a new field alongside `isApplyingRemote`:
```kotlin
@Volatile
private var recentlySwitchedProfile = false
```

Add a `profileSwitchScope` and observer in the `init` block (or the existing startup method where `observeAccountConfigSyncChangedPaths` is called). The observer watches `profileManager.activeProfileId.drop(1)`:

```kotlin
// In init or start() method, add:
scope.launch {
    profileManager.activeProfileId.drop(1).collect {
        recentlySwitchedProfile = true
        delay(2000) // suppress push for 2 seconds after profile switch
        recentlySwitchedProfile = false
    }
}
```

Modify the push guard in the `observeAccountConfigSyncChangedPaths` collect block. Find the existing `if (isApplyingRemote) return@collect` and add the new guard alongside it:


Also add the same guard in the `pushConfigToServerIfNeeded()` or equivalent push method:

```kotlin

```

Add imports: `import com.nexio.tv.core.profile.ProfileManager`, `import kotlinx.coroutines.delay`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Profile switch -> sync push | A profile switch must NOT trigger a sync push that overwrites the previous profile's remote data |
| Non-default profile -> shared settings | Non-default profiles must not edit shared settings (debrid, API keys) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Tampering | AccountSettingsSyncService | mitigate | `recentlySwitchedProfile` flag suppresses push for 2 seconds after `activeProfileId` changes; prevents the `flatMapLatest` re-emission from all 6 stores being interpreted as a settings mutation and triggering a cross-profile push; guard placed alongside existing `isApplyingRemote` check |
| T-02-12 | Tampering | Settings UI (shared settings) | mitigate | `isPrimaryProfile` StateFlow in TraktViewModel and SimklViewModel gates shared settings section visibility; only profile 1 (isPrimary) sees and can edit shared settings; non-primary profiles see only per-profile sections; enforced at ViewModel level per D-07 |
| T-02-13 | Elevation of Privilege | ProfileManager.setActiveProfile | accept | `setActiveProfile` does not validate caller identity — any code path can switch profiles; accepted because profile switching is an in-app action (not a network boundary), and PIN gating is Phase 3 scope (UI-04) |
</threat_model>
